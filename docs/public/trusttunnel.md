# TrustTunnel: проверка транспорта

Статус на 11.10.2026: экспериментальный NodeDriver и независимый node-agent
прошли реальные TCP/UDP проверки выдачи, выборочного отзыва, ротации и срока
действия. После рестарта API/runtime сохранены активные и отозванные назначения.
Драйвер доступен только с явным `experimental_trusttunnel: true` в settings.json;
по умолчанию он выключен. macOS NetworkExtension проходит отдельную приёмку.
Это не обещание production-готовности, reboot/restore и нагрузки.

## Проверенные версии и источники

- Endpoint **1.1.0**, commit `fab5b8353a19332f935fa30869307d37d4a898d1`:
  [исходники](https://github.com/TrustTunnel/TrustTunnel/tree/v1.1.0),
  [настройки](https://github.com/TrustTunnel/TrustTunnel/blob/v1.1.0/CONFIGURATION.md).
- CLI **1.1.11**:
  [документация клиента](https://github.com/TrustTunnel/TrustTunnelClient/blob/v1.1.11/trusttunnel/README.md).
- Подписи официальных бинарников проверяются по
  [инструкции upstream](https://github.com/TrustTunnel/TrustTunnel/blob/v1.1.0/VERIFY_RELEASES.md).
  Фиксируйте конкретную версию и SHA256 проверенного бинарника; SHA256 сам по себе
  не доказывает автора файла.

Результаты относятся к указанным версиям. Документация ветки master может описывать
возможности, отсутствующие в опубликованном endpoint.

## Результаты сетевого испытания

11 октября 2026 года проверен отдельный Linux endpoint и официальный macOS CLI.
Клиент работал через локальный SOCKS; системные VPN, маршруты и DNS Mac не менялись.

| Проверка | Результат |
|---|---|
| HTTPS через HTTP/2 | Проходит |
| HTTPS через HTTP/3 / QUIC | Проходит |
| Внешний IP | Соответствует явно назначенному выходу стенда |
| Неверный закреплённый TLS-сертификат | Соединение отклонено обоими транспортами |
| Новый пароль в credentials.toml + SIGHUP | Старый работает, новый отклоняется |
| Полный restart endpoint после смены пароля | Старый отклоняется, новый работает |

Это не измерение пропускной способности, устойчивости к блокировкам или проверка
NetworkExtension. Производственные назначения и действующие VPN-узлы не переключались.

## Адаптер конфигурации

`orchestrator/infrastructure/drivers/trusttunnel_configuration.py` проверяет
официальный TOML-экспорт и возвращает `TransportConfiguration` с форматом
`trusttunnel-toml`. Пока документ содержит секцию `[endpoint]`; политику маршрутов
и listener добавляет клиентский backend. Адаптер не создаёт доступ и не реализует
NodeDriver, поэтому не зарегистрирован в bootstrap.

- Проверка TLS обязательна; `skip_verification=true` отклоняется.
- Имена полей, типы, размер, адреса и PEM проверяются до передачи клиенту.
- Учётные данные скрыты в repr и ошибках, конфигурация остаётся в памяти.
- Параметры `custom_sni` и `client_random_prefix` пока принимаются только пустыми:
  дополнительные режимы должны получить отдельные испытания.
- Поддержка IPv6 берётся из фактических возможностей узла. Endpoint 1.1.0 при
  экспорте ставит `has_ipv6=true` независимо от своей настройки; адаптер не наследует
  это обещание автоматически.

Экспорты `.conf`, `.vpn` и QR Amnezia не переносятся на TrustTunnel. Upstream умеет
собственный TOML и `tt://` deep link; их включение в публичный API оркестратора
требует отдельного согласованного контракта и испытаний клиентов.

## Воспроизводимая проверка

На подготовленном узле экспортируйте параметры в приватный файл, не в терминал:

```sh
umask 077
trusttunnel_endpoint vpn.toml hosts.toml -c test-client \
  -a YOUR_ENDPOINT_IP:9443 --format toml > endpoint.toml
```

Параметр `--format toml` обязателен: по умолчанию endpoint 1.1.0 печатает deep link.
Передайте файл на машину оператора по защищённому каналу, сохраните права 0600.
После проверки подписи официального клиентского бинарника:

```sh
python scripts/probe_trusttunnel.py \
  --binary /absolute/path/trusttunnel_client \
  --sha256 VERIFIED_BINARY_SHA256 \
  --endpoint-export /private/endpoint.toml \
  --expected-egress EXPECTED_PUBLIC_IP \
  --transport http2
```

Повторите с `--transport http3`. Проверка выполняет запросы к api.ipify.org и
example.com через отдельный SOCKS на loopback; не требует root, не создаёт TUN,
не настраивает системный proxy и не меняет системный VPN. Адрес выхода должен
совпасть с ожидаемым. Временный профиль удаляется, дочерний клиент завершается;
вывод содержит только результаты и длительности, без паролей и тел страниц.
Закройте endpoint и удалите тестовый доступ после испытания.

## Что требуется узловому агенту

У штатного endpoint 1.1.0 нет проверенного API жизненного цикла наших назначений.
Пользователи находятся в файле, а authenticator загружает их в память при старте.
SIGHUP обновляет TLS hosts, но не credentials. Простая запись файла с последующим
SIGHUP не подтверждает ни выдачу, ни отзыв. Перезапуск общего процесса прерывает
подключения его пользователей, поэтому не подходит как обычная операция выдачи.

До включения экспериментального драйвера нужны:

1. Версионированный аутентифицированный API агента и стабильный server_id.
2. Узловой журнал binding_key/remote_id, идемпотентные создание и мутации;
   восстановление прежнего результата после потери ответа или рестарта агента.
3. Применение изменений к работающему runtime с подтверждением. Для revoke —
   прекращение существующих сессий и отказ новым. Для создания одного доступа —
   сохранение сессий остальных клиентов.
4. Локальное исполнение срока доступа даже при недоступном оркестраторе;
   поведение при отказе агента и скачке времени должно быть определено и проверено.
5. Согласованная выдача параметров с состоянием доступа, без секретов в логах.
6. Прохождение общей матрицы драйверов, затем стендовые проверки отказов.

Нельзя выставлять `enforces_expiry`/`confirmed_revoke` только на основании работы
туннеля или успешной записи файла. DriverRegistry отвергает такую реализацию.
Lease и аварийное переключение добавляются лишь после независимого механизма
прекращения доступа на узле. На первом этапе TrustTunnel выбирается явно;
автоматическая межпротокольная миграция не входит в этот прототип.

Предпочтительное следующее исследование — небольшой управляющий слой над
официальной библиотекой TrustTunnel: динамическая авторизация и управление
сессиями. Перед реализацией нужно проверить необходимые точки расширения, чтобы
не обещать подтверждённый отзыв там, где библиотека его не предоставляет.


## Адаптер управляющего API

`trusttunnel.py` реализует порт `NodeDriver`, `trusttunnel_contract.py` описывает
проект API **нашего агента**. Это не API штатного TrustTunnel endpoint.
`node_http.py` содержит общий HTTPS-транспорт с таймаутами, ограниченным пулом,
пределом размера ответа и безопасными ошибками; Amnezia использует тот же транспорт.
Протокольные проверки остаются в отдельных адаптерах.

JSON Schema запросов и ответов: `contracts/trusttunnel-agent.schema.json`.
Проверка `scripts/check_contracts.py` обнаруживает расхождение схемы и моделей.
Контракт пока экспериментальный и может измениться вместе с реализацией агента.
Входящий API backend и схема SQLite этим этапом не меняются.

Все запросы идут по HTTPS со служебным Bearer-токеном узла. Ответ 200 обязан иметь
`Cache-Control: no-store` и общую оболочку: `schema_version: 1`, `server_id`,
`protocol: "trusttunnel"`, `status: "ok"`. Каждый ответ сверяется с ожидаемым узлом.
Перед операцией адаптер проверяет health и обязательные гарантии агента.
Управляющий API и адрес VPN-туннеля — разные адреса/порты.

| Метод | Путь | Запрос / ответ |
|---|---|---|
| GET | `/v1/health` | `Health`: идентичность и три гарантии lifecycle |
| GET | `/v1/clients` | `ClientList`: полный список, максимум 10 000 записей; дубли запрещены |
| POST | `/v1/clients` | `Create` → `ClientSnapshot` |
| GET | `/v1/clients/{id}` | `ClientSnapshot` |
| POST | `/v1/clients/{id}/renew` | `Renewal` → `ClientSnapshot` |
| POST | `/v1/clients/{id}/disable` | `{}` → подтверждённый disabled/expired |
| POST | `/v1/clients/{id}/enable` | `{}` → подтверждённый active |
| POST | `/v1/clients/{id}/replace` | `Replacement` → `ClientSnapshot` |
| GET | `/v1/clients/{id}/connection` | `ConnectionSnapshot`: состояние и параметры одним снимком |

Создание передаёт `external_id` (binding_key), `name`, `expires_at` в UTC с
миллисекундами. Агент назначает `client_id` формата `ttapi_` + 32 hex-символа.
Канонический device_id, пользователи и биллинг остаются за этой границей.
Повтор того же binding должен вернуть тот же ID; другой срок при повторе create —
409, продление выполняется отдельной операцией. Агент сохраняет идемпотентность
после перезапуска. Адаптер не генерирует новые ключи и не повторяет мутации сам.

Продление и замена передают `expires_at` и `idempotency_key`; замена также
`expected_external_id` и `allow_create`. В этом контракте замена обновляет
учётные данные под прежними client_id/binding: старые данные и сессии должны быть
отозваны до подтверждения. При `allow_create: false` отсутствующий runtime-доступ
не создаётся заново; агент возвращает конфликт. Повтор завершённой операции
возвращает её результат, не выполняет повторную ротацию.

Снимок клиента содержит ID, binding, имя, срок, status (active/disabled/expired),
created_at, updated_at. `applied: true` означает, что состояние подтверждено
VPN-runtime, а не только записано в базу. Для disable это включает разрыв текущих
сессий и отказ новых. Ответ active на disable или `applied: false` адаптер отклоняет.
Срок продления и идентичность ответа должны совпадать с запросом.

ConnectionSnapshot дополнительно содержит `endpoint_export` (официальный плоский
TOML, максимум 64 KiB), `ipv6_available` и `transport` (http2/http3).
Username экспорта равен client_id; пароль задаёт и хранит агент. Адаптер проверяет
binding, активность, срок, соответствие username и обязательность TLS, затем
возвращает документ `[endpoint]`. Текст документа скрыт в repr и ошибках.

404, 409, 410 и 422 сохраняют HTTP-смысл, тело ошибки агента наружу не передаётся.
401/403, перенаправление, 405, 429, 5xx и невалидный ответ не запускают fallback;
таймаут оставляет исход неизвестным. Повтор выполняется с тем же binding/ключом.
Для недоступного доступа выдача конфигурации возвращает 410 `access_unavailable`.

**Ограничение этапа:** lifecycle-флаги подтверждены стендом с managed runtime
bridge. Stock endpoint не подходит. Health-ответ сам по себе не доказывает
исполнение гарантий. Leases, экспорт файлов, deep link и QR не включены.
Для теста включите `experimental_trusttunnel` и добавьте отдельный узел через
CLI с `protocol: trusttunnel`, `lease_enabled: false`, отдельным сервисным токеном
и HTTPS origin. Не заменяйте существующую запись AmneziaWG.

При отключении флага уже зарегистрированный TT-узел не станет AWG: проверка
настроек завершится ошибкой. До отката к версии без адаптера отзовите тестовые
назначения с подтверждением и удалите узел штатным CLI. Журнал не откатывается.

## Узловой агент: выполненный этап

В отдельном репозитории `vpn-node` подготовлены Python API/SQLite journal и
MIT authorization/session bridge для pinned TrustTunnel endpoint 1.1.0.
Штатный upstream SIGHUP не используется для управления доступами. Изменение
снимка обновляет authenticator и отменяет forwarding futures отозванного клиента;
агент подтверждает операцию только после runtime acknowledgement.

На стенде проверены два одновременных официальных CLI-клиента: HTTP/2 и HTTP/3,
ожидаемый egress, сохранение identity при повторе, отзыв одного активного TCP-потока
при продолжающейся передаче другого, ротация с отклонением старого пароля и expiry
при выключенном агенте. После re-enable официальный клиент в этом тесте запускался
заново: прозрачное восстановление старого отказавшего соединения не подтверждено.

Реальный UDP DNS через H2/H3, выборочный отзыв UDP и рестарт API/runtime проверены.
Отдельно остаются reboot/restore, macOS NE, защищённое
развёртывание management API и согласование протокола через платформу.
Проверка TCP поверх HTTP/3 не равна проверке UDP forwarding. До закрытия этих
условий production capabilities экспериментального драйвера остаются false.
