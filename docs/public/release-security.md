# Проверки выпуска

Перед публикацией тега выполняются тесты на Python 3.12, 3.13 и 3.14, проверка
архитектуры, типов, форматирования, контрактов, секретов и известных уязвимостей
runtime-зависимостей. Конкретный запуск матрицы подтверждает GitHub Actions;
локальная проверка одной версии Python не подтверждает остальные.

## Зависимости и секреты

```sh
python -m pip install -r requirements-security.txt
python scripts/check_secrets.py
python -m pip_audit -r requirements.lock --no-deps --disable-pip
python scripts/check_workflows.py
```

`pip-audit` обращается к публичной базе PyPI и передаёт названия и версии пакетов.
Ошибка проверки блокирует выпуск; исключений CVE по умолчанию нет. Это проверка
закреплённых runtime-зависимостей, не полный аудит системы, dev/npm-зависимостей или
собственного кода. Отсутствие известных CVE не доказывает безопасность.
[Документация инструмента](https://github.com/pypa/pip-audit).

`detect-secrets` используется офлайн, без проверки найденных ключей через внешние
сервисы. Сканируются отслеживаемые Git файлы текущего снимка, не история коммитов.
Вывод содержит только путь, тип и отпечаток кандидата. Новая находка блокирует выпуск.
В `contracts/secret-baseline.json` перечислены проверенные отпечатки синтетических
тестовых значений, алфавита генератора ID и контрольных сумм закреплённого агента.
Не добавляйте новую находку автоматически: сначала установите её происхождение.
Не сохраняйте реальные секреты под видом исключения.

Все внешние GitHub Actions закреплены на commit SHA. Dependabot предлагает обновления
Actions, pip и npm; изменения всё равно требуют проверки. Сторонние зависимости
инструментов анализа загружаются из реестра: полная фиксация их транзитивных хешей и
защита веток GitHub остаются отдельными задачами сопровождения.

## Происхождение архива

Release job запускается только после verify, проверяет соответствие тега VERSION
и собирает архив из точного Git-коммита. Он не включает runtime-журналы или настройки.
Gzip timestamp фиксирован: повторная упаковка одного коммита даёт те же байты.

Перед публикацией `actions/attest` создаёт GitHub/Sigstore attestation для `.tar.gz`.
Права записи и OIDC есть только у release job. При отказе attestation публикация не
выполняется. Это подтверждает происхождение артефакта, а не качество его исходников.
[Механизм GitHub](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).

Скачанный архив проверьте перед запуском установщика/обновления:

```sh
gh attestation verify undercore-orchestrator-vX.Y.Z.tar.gz \
  --repo UndercoreCo/orchestrator \
  --signer-workflow UndercoreCo/orchestrator/.github/workflows/release.yml
shasum -a 256 -c SHA256SUMS
```

Updater по-прежнему проверяет содержимое, checksum, совместимость и миграцию; сам он
не запрашивает GitHub attestation. Проверка выше — отдельный шаг оператора. Старые
выпуски без attestation не получают её задним числом. Для v0.5.1 повторная упаковка точного тега и строгая проверка attestation
подтвердили совпадение опубликованных байтов с исходным коммитом 26.10.2026.
Release job тогда остановился на уже существующем релизе, а не на проверках кода.
Новая процедура ниже устраняет конфликт повторной публикации.


## Единственный путь публикации

Выпускаемый коммит должен быть в истории `main`, тег — точно `vVERSION`.
Workflow сериализован по тегу и не отменяет уже идущую публикацию. После сборки и
attestation `scripts/publish_release.py` проверяет source commit/ref, signer workflow
и GitHub-hosted runner. Новый релиз создаётся черновиком; после загрузки и побайтной
сверки обоих файлов становится публичным.

Повторный запуск проверяет существующий релиз: совпадают имена, размеры и байты
архива/SHA256SUMS. Только полный идентичный черновик можно допубликовать. Идентичный
публичный релиз не изменяется. Отличающийся/неполный набор, ошибка сети или
авторизации останавливают процесс; перезапись assets, перенос тегов и `--clobber`
не используются. Неполный черновик требует операторского разбора, а не скрытого ремонта.
Не создавать релиз параллельно вручную. Изменение байтов требует новой версии.

Автоматическое обновление установленной службы не включается публикацией тега.
Проверка и применение установленного релиза остаются отдельной процедурой.
