# Разработка протокольного драйвера

Реализован AmneziaWG и экспериментальный [TrustTunnel](trusttunnel.md).
TrustTunnel регистрируется в bootstrap только с `experimental_trusttunnel: true`.
Оба требуют совместимого агента; публичная поставка агентов ещё не завершена.
[Матрица реализации и поставки](support.md). Внешней plugin-системы и загрузки произвольного Python-кода
из настроек нет: новый драйвер добавляется проверяемым изменением репозитория.

## Граница ответственности

[NodeDriver](https://github.com/UndercoreCo/orchestrator/blob/main/orchestrator/application/ports.py) описывает операции драйвера.
Оркестратор выбирает узел, сохраняет назначение, контролирует ревизии и переключения.
Драйвер знает протокол узла, проверяет ответы, выдаёт транспортные параметры и
выбирает форматы экспорта. Backend решает вопросы пользователя и права на доступ.

| Метод | Обязанность |
|---|---|
| verify | Проверить идентичность узла до включения в реестр |
| observe/list | Проверить идентичность узла, получить наблюдение и клиентов |
| create | Повторяемо создать доступ по стабильному binding_key |
| get/validate | Проверить состояние и соответствие remote_id/external_id |
| mutate | Продлить, включить, отозвать или заменить доступ с сохранением повторяемости |
| connection | Вернуть согласованные состояние и транспортные параметры |
| configuration | Вернуть типизированный документ движка |
| export | Выбрать и валидировать представление, вернуть ExportDocument |

Повтор create после потери ответа должен найти тот же peer. Срок должен исполняться
на узле. Отзыв требует подтверждения: таймаут API не означает успешного удаления.
Без этих трёх гарантий DriverRegistry не принимает драйвер.

## Порядок реализации

1. Опишите реальные возможности API целевого узла и его гарантии при сбоях.
2. Реализуйте адаптер транспорта отдельно от протокольных проверок. Смотрите
   `amnezia_http.py` и `amneziawg.py` как текущий пример, а не обязательный wire-формат.
3. Реализуйте NodeDriver и DriverCapabilities, включая поддерживаемые экспорты.
4. Зарегистрируйте драйвер в `bootstrap.py`; обновите разрешённые протоколы в
   моделях, реестре и проверке настроек, если добавляется новое имя протокола.
5. Добавьте соответствие protocol/format в TransportConfiguration и схемы.
6. Если узел поддерживает lease, реализуйте `LeaseTransport` (probe/observe/renew)
   и зарегистрируйте его в `LeaseRegistry` через bootstrap. Нельзя включать
   lease_enabled без независимого прекращения доступа на узле и тестов fencing.
   Прикладной сценарий использует только LeaseObservation и LeaseGrant.
7. Пересоберите контракты, обновите документацию и включайте capability только
   после полного прохождения жизненного цикла.

Одна реализация export не делает WireGuard или TrustTunnel рабочим драйвером.
Динамическое определение доступных экспортов уже есть; общий PNG renderer не
должен выбирать узел или понимать аккаунты.

## Обязательная матрица проверок

| Сценарий | Ожидаемый результат |
|---|---|
| Повтор создания | Тот же remote_id, без второго peer |
| Потерян ответ мутации | Повтор использует прежнюю идентичность/ключ |
| Неверный server_id или binding | Отказ выдачи конфигурации |
| Истёкший/отключённый доступ | Нет экспорта; срок исполняется узлом |
| Неподтверждённый отзыв | Переключение не объявляется завершённым |
| Перезапуск controller | Незавершённая операция продолжает прежнюю цель |
| Несовместимый клиент/формат | Явная ошибка без скрытой замены протокола |
| Ошибка upstream | Нет секретов в ответе, repr, CLI и журналах |

`tests/test_driver_contract.py` — общий параметризованный набор: повтор создания,
потеря ответа, подтверждённый отзыв, запрет экспорта после истечения срока,
проверка binding и доступные форматы. Сейчас он запускается с реальным адаптером
Amnezia против двух вариантов HTTP-контракта закреплённого агента; kernel заменён
тестовой реализацией. Для нового протокола добавьте fixture с его реальным адаптером,
API и способом управлять временем/сбоями, сохранив общие проверки.

Сценарии переключения, fencing и восстановления проверяются дополнительно в
`test_node_switch`, `test_leases`, `test_connection_contract` и `test_exports`.
Общий набор не заменяет эту матрицу и проверку на реальном узле. Тестовый transport
TrustTunnel в проверке границ доказывает только внедрение зависимости; managed-адаптер TrustTunnel дополнительно прошёл реальные TCP/UDP проверки
на выделенном стенде. Он включается явным experimental_trusttunnel, без leases.
