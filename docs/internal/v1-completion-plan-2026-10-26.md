# План завершения публичного Orchestrator 1.0

Дата: 26.10.2026 (Asia/Tashkent). Статус: направление согласовано владельцем; начат этап 0.
Запрос владельца: самостоятельный оркестратор, автономные адаптеры в том же
репозитории, установка из публичного выпуска с конфигом, обновления,
версионирование, универсальный API и понятная архитектура для внешних разработчиков.
Документ не разрешает production-изменения и не утверждает готовность будущих команд.

## Границы продукта 1.0

Backend заказчика отвечает за пользователя, оплату, слоты и разрешённый срок.
Оркестратор отвечает за техническое назначение, выбор узла, операции и восстановление.
Адаптер/агент отвечает за VPN runtime, ключи, экспорт, исполнение срока и отзыв.
Учёт трафика остаётся на узле, бизнес-агрегация и квоты — в системе заказчика.
Оркестратор передаёт измерения, не становится биллингом.

Один controller с локальной SQLite; без active-active. Контроллер не пропускает
пользовательский трафик. CLI/панель не требуют сайта Undercore.
Цель первого поддерживаемого окружения: Ubuntu 24.04 LTS, Linux amd64, systemd.
Это предлагаемая граница приёмки, а не обещание непроверенной совместимости.
Поддерживаемые транспорты: AWG и TrustTunnel после отдельной полной приёмки каждого.
Обычный WireGuard не объявлять поддерживаемым только по наличию экспортера.

## Структура общей поставки

```text
orchestrator/                 # существующие слои ядра
adapters/
  amneziawg/                 # самостоятельный пакет, node API, runtime binding, тесты
  trusttunnel/               # самостоятельный пакет, node API, runtime binding, тесты
contracts/
  backend/                   # OpenAPI для интеграторов
  adapter/                   # версия общего контракта адаптера
  compatibility.json         # проверенные комбинации компонентов
packaging/                   # bootstrap, installer, updater, systemd, release manifest
examples/                    # фиктивные настройки, минимальный сторонний backend
tests/                      # интеграционные и сквозные проверки
docs/public/                # quickstart, API, разработка, эксплуатация
```

У адаптеров собственные зависимости, версии, артефакты, настройки, состояние и
службы. Они устанавливаются и обновляются отдельно, работают без импорта ядра.
Адаптер и node-agent могут быть одной службой на VPN-узле: дополнительный
прокси-процесс только ради структуры не нужен. Общий HTTP-клиент ядра обращается
к версионированному контракту; протокольные поля/экспорты остаются у адаптера.
Текущий NodeDriver использовать как основу границы миграции, а не переписывать
жизненный цикл с нуля. Не включать произвольную загрузку кода из настроек.

## Этапы и критерии завершения

### 0. Единый исходный код и достоверные статусы

Свести main с выпущенным кодом после проверки различий; инвентаризировать локальные
изменения и не публиковать их автоматически. Сверить release assets с точным
коммитом и attestation. Устранить конкурирующие способы публикации; повтор запуска
не должен перезаписывать существующий релиз с другими байтами.
Обновить README/roadmap/матрицу поддерживаемого. Завести задачи с приёмкой.
Готово: clean checkout публичного тега содержит всё заявленное, документация
соответствует коду, повтор публикации безопасно проверяет уже существующий результат.

### 1. Устойчивость управления (VPN-01, VPN-03)

Разделить срок разрешённого пользователю доступа, свежесть управления узлом и
условие безопасного переноса. Спроектировать ограниченную автономность уже выданных
доступов при недоступном controller. Не продлевать права автоматически и не выдавать
новые по устаревшим данным. Агент сохраняет срок и подтверждённые запреты на диске.
Отдельно определить максимально допустимую задержку отзыва при потере связи.

Ключевой компромисс: если старый peer разрешено обслуживать автономно, нельзя
одновременно считать его закрытым по прежнему короткому lease и выдавать замену.
До подтверждённого отзыва или истечения всего автономного разрешения перенос ждёт.
Варианты доступности/переключения должны быть явной политикой с безопасными bounds;
простое выключение lease или увеличение TTL не считается решением.

Резервные адреса управления проверяют ту же идентичность узла и TLS, не создают
новый узел. Добавить контроль срока сертификатов TrustTunnel и проверенную ротацию.
Готово: partition, crash, reboot, expiry, pending revoke, потеря ответа и возврат
связи проходят; старые запреты сохраняются, дубликатов нет, tunnel/control health
не подменяют друг друга. Проверить часы и безопасное поведение при их расхождении.

### 2. Общий контракт и самостоятельные адаптеры (VPN-05, VPN-06)

Извлечь рабочие исходники по allowlist без ключей/журналов, сохранить лицензии и
происхождение runtime. Каждый адаптер реализует capabilities, identity, create,
get, renew, revoke, configuration/export и доступные usage/health/lease возможности.
Семантика повторов/неизвестного результата обязательна; capabilities не заменяют
общую матрицу lifecycle. Протокольные форматы определяет адаптер.
Миграция существующих узлов сохраняет ключи, назначения и незавершённые операции.
Готово: обе службы собираются отдельно из общего публичного тега, проходят общий
набор контрактных тестов и реальные подключения; ядро не импортирует их runtime.

### 3. Контракт API для сторонних систем

Сохранить рабочий v2. Довести OpenAPI, примеры запросов/ответов/ошибок,
идемпотентность, timeout/retry, revision, capabilities, форматы экспортов и
пагинацию до полного соответствия runtime. Не переименовывать API ради косметики.
Добавить идентичность вызывающей системы, отдельные ключи, область доступа,
ротацию и namespace устройств: чужой device_id не позволяет читать/отзывать доступ.
Существующую интеграцию перевести через совместимый default namespace.
Ключ backend не даёт права менять настройки/узлы/обновления.
Готово: минимальный сторонний backend проходит create/config/export/renew/revoke,
две интеграции с одинаковыми device_id изолированы; legacy Undercore продолжает работать.

### 4. Установка из публичного релиза (VPN-04)

Bootstrap получает фиксированный релиз, проверяет происхождение и целостность,
принимает config, проверяет окружение/конфликты и устанавливает службу с минимумом
прав. Не требуется checkout личных папок или внутренние deploy-скрипты.
Различать установку controller, установку adapter+VPN на узле и регистрацию
готового узла. Runtime оркестратора не получает SSH/root для выдачи подключения.
Повтор установки безопасен и не сбрасывает ключи/данные; частичный отказ объясним.
Политика в конфиге, секреты в файлах/secret references, журнал в state directory.
Для nodes явно выбрать декларативную модель или однократный bootstrap реестра:
сейчас повторное редактирование JSON не заменяет уже импортированный SQLite registry.
Готово: публичная инструкция и одна команда на каждой чистой VM дают рабочую
систему; без секретов проекта, ручной правки исходников и затрагивания чужого VPN.

### 5. Версии и обновления

SemVer отдельно для controller и самостоятельных adapters; suite manifest фиксирует
совместимые версии. Независимы версии API, настроек, схемы БД и документов туннеля.
Каналы stable/beta, changelog, политика снятия поддержки и срок сохранения старого API.
Одна CI-цепочка сборки/проверки/attestation/публикации; SBOM, зависимости и лицензии.
Обновления получают опубликованные проверенные релизы, не произвольные коммиты main.
Предлагаемые команды (пока не обещать их существование): update check, update --to,
rollback. Текущие install.py/update.py переиспользовать.
Проверка происхождения встроена в updater; preflight, rehearsal migration, backup,
readiness и совместимый rollback обязательны. Не восстанавливать старую БД поверх
новых операций. По умолчанию применение явное; автоприменение — отдельная opt-in
политика с окном обслуживания и ограничением совместимых версий.
Готово: чистая установка N, обновление N→N+1, отказ на каждом этапе и rollback
воспроизводимы; соединения/ключи/журнал/запреты сохраняются.

### 6. Публичная приёмка 1.0

Один README: назначение, границы, установка, обновление, первый запрос.
Карта слоёв, описание одного полного сценария, ADR для важных решений,
CONTRIBUTING/SECURITY, тестовый adapter и пример стороннего backend.
Нагрузочный профиль с заявленной ёмкостью, p95/p99 и поведением при перегрузке;
метрики без секретов, audit административных операций, полезный doctor.
Проверить заполненный диск/БД, потерю worker, сертификат, недоступный узел,
истечение доступа, возврат сети, backup и перенос на чистый controller с остановкой
старого. Restore требует сверки с реальными узлами, а не только целого SQLite.
Предлагаем 72 часа стендового прогона с контролируемыми сбоями после принятия
нагрузочных критериев. Внешний разработчик повторяет quickstart без нашей помощи.
Готово: выполнена фиксированная матрица, нет незакрытых блокирующих дефектов,
оба транспорта имеют честный supported status; опубликован 1.0.0.
