# Устойчивость управляющей связи: подэтап 1a

Изменения в отдельной ветке, без выпуска и без команд рабочим VPN-узлам.
Родительская задача: https://github.com/UndercoreCo/orchestrator/issues/8.

## Выявленный риск

Lease v1 действует 90 секунд. Потеря controller останавливает весь управляемый
контейнер после истечения разрешения. Простое увеличение этого срока небезопасно:
при переносе NodeLeases.fence вычислял ожидание из текущих настроек, а не из
параметров ранее выданного разрешения. Уменьшение настроек после перезапуска могло
уменьшить ранее выбранный запас безопасности. Для автономного разрешения этот
дефект создаёт риск двух одновременно разрешённых доступов.

## Реализовано

- SQLite хранит наибольшее применённое `fence_window_seconds` для узла.
- Резервирование sequence, срока и окна выполняется одной транзакцией до HTTP.
- Потерянный ответ не позволяет забыть потенциально выданное разрешение.
- Heartbeat с меньшей политикой и restore не уменьшают окно.
- Fencing использует максимум сохранённого и текущего окна и сохраняет результат.
- После смены boot отсчитывается полное сохранённое окно по монотонным часам.
  Повторный опрос в том же boot не сдвигает дедлайн.
- Подтверждённый отзыв исходного peer сохраняет быстрый перенос.
- Схема 2 мигрирует известные схемы 0/1 атомарно. Для старых leases окно 900
  секунд (прежние максимумы 300+600), активные fences начинают отсчёт заново.
- Backup/restore сохраняет окно; повреждённый журнал не исправляется автоматически.

`tests/test_fence_window.py` проверяет меньшую политику после перезапуска,
потерю ответа, reboot, отсутствие выдачи на цели раньше границы, явный отзыв и
ошибку записи журнала до отправки команды. `test_storage_upgrade.py` проверяет
миграцию 0/1, атомарный отказ, сохранение запретов, identity и запрещённый откат.
Закреплённый агент и его контрольные суммы не изменены.

Локальная проверка: 389 тестов прошли (Python 3.14); ruff, mypy, контракты,
границы архитектуры, проверка workflow и сборка документации успешны.
Интеграционные тесты используют закреплённый Engine с подменой VPN backend;
живой сетевой отказ и реальный root runtime этим набором не проверялись.

## Следующая часть

1. Подготовить переходный релиз для чтения схем 1/2 без автоматической миграции
   схемы 1; он должен соблюдать сохранённую границу схемы 2 и использовать
   консервативные 900 секунд для схемы 1. Текущий updater правильно отклоняет
   прямой переход с 0.5.1: старый код не умеет безопасно читать новую схему.
2. Специфицировать отдельные freshness и разрешение обслуживать ранее выданные
   peer. Политика задаёт предел автономности и соответствующую задержку отзыва.
   Истечение пользовательского доступа и уже сохранённый запрет остаются обязательными.
3. Реализовать протокол в собственном исходнике агента, затем обновить закреплённую
   тестовую копию с provenance. Не менять fixture отдельно от реального агента.
4. Проверить разрыв сети, рестарт агента/runtime, сдвиги часов, потерю ответа,
   отключение во время разделения сети, восстановление без воскрешения старых peer.
5. Проверить резервный управляющий маршрут и ротацию сертификата TrustTunnel.
6. Только после этих проверок подготовить согласованный стендовый/production rollout.

Этот подэтап сам по себе не устраняет отключение через 90 секунд. Новые настройки
автономности, новые версии протокола, релизы и production-изменения не включены.
